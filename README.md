# Simple AI Chat UI

## 1. プロジェクト概要

Claude APIを利用して、ユーザーとAIがテキストで会話できるシンプルなWebアプリケーションを開発する。

AIの回答をストリーミング方式で表示し、同じページ内で会話履歴を保持できるチャットアプリを目指す。

本プロジェクトでは、要件定義・システム設計・画面構築・API連携・エラー処理・検証までの一連の開発工程を学習する。

### プロジェクト情報

| 項目 | 内容 |
|---|---|
| プロジェクト名 | ai-chat |
| アプリ名 | Simple AI Chat |
| 開発環境 | Windows 11 / VS Code |
| フレームワーク | Next.js 16.4.3 |
| 言語 | TypeScript |
| UI | React / Tailwind CSS |
| AIモデル | Claude Haiku 5.5 |
| API連携 | Vercel AI SDK（ai 7 / @ai-sdk/anthropic 4 / @ai-sdk/react 4） |
| 開発方式 | ローカル開発 |
| 公開 | Vercel公開は後日検討 |

## 5. 要件定義 v1.0

### 5.1 基本機能

- ユーザーが文章を入力できる
- Enterで送信できる
- Shift+Enterで改行できる
- 最大2,000文字まで入力できる
- 空欄・空白のみでは送信できない
- 送信後に入力欄をクリアする
- ユーザーのメッセージを右側に表示する
- AIの回答を左側に表示する

### 5.2 AI連携

- Claude Haiku 5.5を利用する
- Claude APIへ質問を送信する
- システムプロンプトは汎用アシスタントとする
- 最大出力を1,024トークンとする
- 回答をストリーミングで逐次表示する

### 5.3 会話履歴

- 同一ページ内で会話履歴を保持する
- Claude APIへ送る履歴は正常完了した直近10往復と今回の質問
- ページリロードで履歴を削除する
- データベースへの永続保存は行わない

### 5.4 送信制御

- AI回答中の追加送信を禁止する
- 回答完了後に新しい質問を送信できる
- 回答停止ボタンは設けない

### 5.5 エラー処理

- エラーの原因を分かりやすく表示する
- エラー表示はチャット画面内に配置する
- 通信失敗時は入力した質問を保持する
- 再試行ボタンを設置する
- 再試行時に同じ質問を二重登録しない
- 未完成のAI回答は破棄する
- 回答生成全体のタイムアウトは暫定60秒とする

- Enter：送信
- Shift+Enter：改行

### 9.5 入力制限

- 文字数上限：2,000文字
- 空欄送信：禁止
- 送信後：入力欄をクリア

### 9.7 ChatInput.tsxへの入力処理の分割

### 9.9 Claude API連携とストリーミング表示（STEP 2・3）

Vercel AI SDKを導入し、Claude Haiku 5.5の回答を少しずつ表示する仕組みを実装した。

STEP 2（API連携）とSTEP 3（ストリーミング）は、useChatがストリーミングを前提とした仕組みのため、まとめて実装した。

#### 通信の流れ

```text
ブラウザ（Chat.tsx / useChat）
  ↓ 会話履歴をPOST送信
Next.jsサーバー（app/api/chat/route.ts）
  ↓ APIキーを付けて送信
Claude API（claude-haiku-5-5）
  ↓ 回答を少しずつ返す
Next.jsサーバー → ブラウザ（届いた部分から表示）
```

#### 追加したライブラリ

| パッケージ | バージョン | 用途 |
|---|---|---|
| ai | 7.0.153 | streamTextなどのAI SDK本体 |
| @ai-sdk/anthropic | 4.0.88 | Claude APIとの接続 |
| @ai-sdk/react | 4.0.157 | useChat |

#### APIルートの設定（route.ts）

| 項目 | 設定 |
|---|---|
| モデル | claude-haiku-5-5 |
| システムプロンプト（instructions） | あなたは親切で丁寧な汎用アシスタントです。 |
| 最大出力トークン（maxOutputTokens） | 1,024 |
| 思考（reasoning） | none（無効） |

reasoningを無効にした理由：Claude Haiku 5.5は標準で回答前に思考（thinking）を行い、その分のトークンも最大出力1,024に含まれる。思考で上限を使い切り回答が途中で切れることを防ぐため、思考を無効にした。

#### Chat.tsxの変更

- 会話履歴のuseStateをuseChatのmessagesへ置き換えた
- 送信はuseChatのsendMessageで行う
- useChatのstatus（submitted・streaming）から「回答中」を判定し、回答中は送信しない
- useChatのメッセージ（partsの配列）を、MessageListが受け取る形式（id・role・content）へ変換して渡す
- 仮の初期メッセージ（「こんにちは！」の2件）を削除した。最初は空の画面から会話を始める

#### ChatInput.tsxの変更

- PropsにisResponding（回答中かどうか）を追加
- 回答中は送信ボタンを無効にする（入力欄への入力は可能）

### 9.10 会話履歴の制限（STEP 4）

#### 仕様

- Claude APIへ送る履歴は「正常に完了した直近10往復＋今回の質問」
- 画面の表示は制限しない（すべての会話が表示されたまま）
- ページのリロードで履歴は消える
- データベースなどへの保存はしない

#### 1往復の数え方

「ユーザーの質問」の直後に「文章のあるAIの回答」が続いた組を1往復とする。

| AIの回答が空 | 往復に数えず、APIへ送らない |

### 9.11 エラー処理（STEP 5）

#### 仕様と実装

| 要件（5.5） | 実装 |
|---|---|
| エラーの原因を分かりやすく表示する | 原因ごとに日本語のメッセージを表示（下表） |
| エラー表示はチャット画面内に配置する | 吹き出しエリアの最後に赤い枠で表示（ChatError.tsx） |
| 通信失敗時は入力した質問を保持する | 失敗した質問は吹き出しとして残す |
| 再試行ボタンを設置する | エラー表示の右側に「再試行」ボタン |
| 再試行時に同じ質問を二重登録しない | useChatのregenerateで、最後の質問を追加せずに送り直す |
| 未完成のAI回答は破棄する | エラー発生時に、途中まで表示されたAIの回答を削除する |
| タイムアウトは暫定60秒 | streamTextのtimeout（totalMs: 60,000）。中断を「エラー」に変換して画面に表示 |
| サーバー側で入力内容を再検証する（7章・11章） | lib/chat-validation.tsで検証し、問題があれば400で返す |
| 回答中の通信の途切れ（ブラウザ側） | 回答中に20秒間なにも届かなければ、通信を止めて未完成回答を破棄し、エラーと再試行ボタンを表示（Chat.tsx） |

#### ブラウザ確認で見つかった問題と修正

- 症状：回答の途中で開発者ツールを「オフライン」にすると、エラーも再試行ボタンも表示されず、送信ボタンも無効のまま固まった。オンラインに戻しても動かなかった
- 原因：途中で止まった通信は「切断」として通知されないため、ブラウザが回答の続きを待ち続け、状態が「受信中」のままになっていた。サーバーは送信を終えたつもりのため、サーバー側の60秒タイムアウトでは検出できない
- 修正1：ブラウザ側に見張りのタイマー（20秒）を追加。新しい文字が届くたびにやり直し、20秒間なにも届かなければ通信を止めてエラーを表示する
- 修正1の再確認で、同じ症状が続いた（20秒以上待っても、送信ボタンがグレーのまま）
- 原因2：開発者ツールの「オフライン」中は、通信の中断（stop）が完了せず、useChatの状態が「受信中」のまま戻らない可能性がある。その場合、タイマーが動いても「受信中は表示しない」条件によりエラーが表示されない
- 修正2：タイマーが通信の途切れを検出した時点で、useChatの状態に関係なく「回答中ではない」と扱うようにした
- 修正2の検証：ヘッドレスChrome（画面を表示しないChrome）で、途中で止まる偽のサーバーを使って再現テストを実施。通常の場合と、通信の中断が効かない場合の両方で、約20秒後にエラーが表示され、送信ボタンが有効になり、再試行で質問が1件のまま回答が表示されることを確認。Claude APIとは通信していない
- 修正2の再確認でも、同じ症状が複数回再現した（途中までの回答が残り、エラーも再試行ボタンも出ない）
- 原因3（仕組みとしては確認済み。ただし今回の症状の本当の原因ではなかった。下記「最終的に分かった本当の原因」を参照）：通信が「完了の合図（finish）」なしで正常に閉じられると、useChatはエラーではなく「待機中（ready）」に戻る。onErrorも呼ばれないため、未完成回答が残り、エラーも表示されない。待機中に戻るので見張りタイマーも止まる。Node.jsとヘッドレスChromeで再現して確認した
- 修正3：useChatのonFinishで、完了の理由（finishReason）がないまま終わった場合を「通信の途切れ」と判断し、未完成回答の破棄とエラー表示を行う。正常に完了した回答には、サーバーから必ず`finishReason: "stop"`が届くことを確認済み
- 修正3の検証（ヘッドレスChrome・料金なし）：「途中で正常に閉じる」「途中で止まる」「正常に完了」の3パターンを確認。前の2つはエラーと再試行ボタンが表示され、再試行で質問1件のまま回答が表示された。正常に完了した場合はエラーが出なかった。偽のClaude API（ANTHROPIC_BASE_URLで差し替え）を使い、本物のroute.tsを通した正常な回答でもエラーが出ないことを確認した
- ヘッドレスChromeでブラウザの命令から「オフライン」にしても、既存のlocalhost通信は止まらず、開発者ツールの画面操作と同じ状態を再現できなかった。そのため、本物の開発者ツールの「オフライン」での再確認は未実施

#### 最終的に分かった本当の原因：最大出力トークンの上限

- ブラウザの開発者ツールで確認したところ、/api/chatの通信はステータス200で、失敗（failed）していなかった。コンソールにもアプリのエラーはなかった
- 「日本の歴史を詳しく説明して」の回答は長く、最大出力1,024トークン（要件5.2）に達して、文の途中で打ち切られていた（finishReason: "length"）。これは正常な終わり方なので、エラーも再試行ボタンも表示されない
- 開発者ツールの「オフライン」は、すでに始まっていたlocalhostの通信を止めていなかった（ヘッドレスChromeの実験結果とも一致）
- 修正1〜3（見張りタイマー・状態に頼らない判定・完了の合図の確認）は、本当に通信が途切れた場合の対策として残す
- 本当の通信切断を試すには、回答の途中で開発サーバーを停止する（Ctrl + C）方法を使う

### 9.17 ログイン機能（合言葉）

自分と少人数の知り合いだけが使えるよう、合言葉（パスワード）によるログイン機能を追加した。Next.js 16の認証ガイド（Stateless Sessions・Proxy・Route Handlerでの確認）に沿って実装した。

#### 仕組み

| 部分 | 内容 |
|---|---|
| 合言葉 | `.env.local`の`APP_PASSWORD`。全員で同じ合言葉を使う |
| ログイン画面 | `/login`。合言葉を入力する |
| ログイン状態 | 合言葉が正しければ、署名付きのcookie（jose・HS256）を7日間保存する |
| 署名用の鍵 | `.env.local`の`AUTH_SECRET`（32文字以上）。cookieが偽造・改ざんされていないかを確かめる |
| 守り方①（proxy.ts） | ログインしていない人がページを開くとログイン画面へ移動させ、APIには401を返す |
| 守り方②（route.ts） | APIの中でももう一度ログインを確かめる（proxyだけに頼らない） |
| ログアウト | 画面右上の「ログアウト」でcookieを削除し、ログイン画面へ戻る |
| ログインの期限切れ | チャット中に期限が切れると、「ログインの有効期限が切れました…」と表示する |

#### 安全のための工夫

| 工夫 | 理由 |
|---|---|
| cookieをhttpOnlyにする | ブラウザのJavaScriptから読めないようにし、盗まれにくくする |
| cookieをsameSite=laxにする | 他のサイトからの送信に使われにくくする |
| 公開時はsecure（HTTPSのみ）にする | 通信途中で盗み見られないようにする（ローカルの開発中はHTTPのため無効） |
| 合言葉は比較時間が一定の方法で比べる | 比較にかかる時間の差から、合言葉を推測されないようにする |
| 合言葉を間違えたら1秒待たせる | 総当たりで試されにくくする |
| 設定がないときはログインできない | 合言葉や鍵の設定忘れで、誰でも入れる状態にならないようにする |

#### 必要な設定（.env.local）

```text
APP_PASSWORD=自分で決めた合言葉（長く推測されにくいもの）
AUTH_SECRET=ランダムな32文字以上の文字列
```

`AUTH_SECRET`は次のコマンドで作れる（実行するたびに違う文字列が出る）。

```text
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

`.env.local`を変更したら、開発サーバーを再起動する。

#### 制限事項

- 合言葉は全員共通のため、特定の人だけ使えなくすることはできない（合言葉を変えると全員が再ログインになる）
- ログイン状態はcookieだけで管理している（サーバーに記録しない）。ログアウトするとブラウザからcookieは消えるが、もしcookieが盗まれていた場合、期限（7日）まではそのcookieが使える。全員のログインを無効にしたいときは`AUTH_SECRET`を変更する
- 間違えたときの1秒の待ち時間は、同時に何回も試す攻撃までは防げない。合言葉は長く推測されにくいものにする

## 11. セキュリティ方針

- APIキーは.env.localで管理する
- APIキーをブラウザへ渡さない
- APIキーをソースコードへ直接記載しない
- サーバー側で入力内容を検証する
- 秘密情報をエラーメッセージに含めない
- 公開前にAPI利用制限と料金管理を検討する
- 合言葉によるログインで、使える人を限定する（9.17）

※APIキーは.env.localに設定済み（Gitの管理対象外）。APIキーはサーバー側（route.ts）でのみ環境変数ANTHROPIC_API_KEYから読み込まれ、ブラウザには渡らない。

#### 公開（デプロイ）前に対応が必要なこと

現在はローカル（自分のパソコン）だけで使っているため問題ないが、インターネットに公開する場合は以下が必要。

- **利用制限**：合言葉によるログイン機能を追加済み（9.17）。合言葉を知っている人だけが使える。さらに安全にするには、1人あたりの回数制限（レート制限）も検討する
- **料金の上限**：Claude Consoleで、APIキーの利用上限額を設定する
- **送信データの大きさの制限がない**：大量の履歴を送られても、Claudeへ送るのは直近10往復だが、受け取り処理の負荷にはなる
- **会話履歴はブラウザから送られる**：AIの回答の部分も書き換えて送ることができる（サーバーに履歴を保存しない設計のため）。重要な判断にこのアプリの回答を使わない
